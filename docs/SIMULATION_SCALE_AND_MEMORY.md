# raWWar — Simulation Scale and Memory Model\n\nStatus: Living architecture model.\n\n> **The question is not “How many things exist?” The question is “How much authoritative state must exist, and how often must that state do work?”**\n\nraWWar needs to represent a galaxy without pretending that every object requires the same simulation frequency.\n\n## 1. Bytes are a GPU-friendly state unit\n\nThe proposed state-plane representation uses an 8-bit channel as a compact state index:\n- one channel = one byte;\n- one byte = 256 representable values;\n- if 0 is reserved for inactive/uninitialized, 1–255 provide 255 usable state indexes;\n- one RGBA8 pixel = four independent channels = four independent byte-sized state values.\n\n| Representation | Raw state storage |\n|---|---:|\n| 1 FSM state channel | 1 byte |\n| 4 FSM state channels | 4 bytes |\n| 1 RGBA8 pixel | 4 bytes |\n| 16 FSM state channels | 16 bytes |\n| 32 FSM state channels | 32 bytes |\n| 64 FSM state channels | 64 bytes |\n| 128 FSM state channels | 128 bytes |\n\nThis is a state plane, not the complete object. The byte answers: **where is this FSM in its state machine right now?** It does not contain the FSM definition, identity, relationships, history, or arbitrary semantic data.\n\n## 2. 255 states does not mean 255 FSMs\n\nIf one channel represents one FSM instance, that channel can hold a state index from 0–255. One RGBA8 pixel therefore represents four FSM instances, each with an 8-bit current-state value.\n\nA complicated soldier is consequently a collection of cooperating FSMs rather than one giant machine. Candidate examples include locomotion, balance, weapon handling, perception, communication, navigation, qualification, procedure, medical/condition, social/activity, and command-response FSMs.\n\n## 3. Soldier complexity budget\n\nraWWar soldiers are persistent people, not simple RTS minions. They have identity, skills, qualifications, rank, assignments, equipment, relationships, condition, experience, history, current task, authority, location, and concurrent procedures.\n\nThe exact FSM count is not hard canon yet. A useful initial architecture budget is:\n\n| Soldier tier | Concurrent FSM capacity | Raw FSM state plane |\n|---|---:|---:|\n| Background population | 4–8 | 4–8 bytes |\n| Ordinary persistent soldier | 16–32 | 16–32 bytes |\n| Highly active soldier | 32–64 | 32–64 bytes |\n| Command/specialist complexity | 64–128 | 64–128 bytes |\n\nThese are capacity targets, not promises that every slot is active.\n\nAt 100,000 soldiers, 32 bytes of FSM state per soldier is about 3.05 MiB. At 1,000,000 soldiers it is about 30.5 MiB. At 10,000,000 soldiers it is about 305 MiB. That is only the hot FSM-state plane, not complete soldier data.\n\n## 4. FSM definitions are shared\n\nFSM definitions should not be duplicated per soldier.\n\nFSM Definition → many FSM Instances → individual state byte\n\nThousands of infantry can share the same locomotion FSM definition while having different state values, skills, equipment, history, orders, and conditions.\n\nState-plane memory therefore scales with instances; behavior definitions scale with distinct procedures.\n\n## 5. The galaxy uses the same idea at another scale\n\nA galaxy can have a spatial state field. The field should represent the coarse authoritative state needed to decide what deserves more detailed simulation.\n\nCandidate sector fields include ownership, population band, industrial activity, military activity, conflict state, logistics pressure, strategic importance, research activity, political instability, travel activity, event pressure, and simulation priority.\n\nThe galaxy texture is a representation of state, not the complete semantic world model.\n\n## 6. Concrete texture sizes\n\nFor an RGBA8 2D texture:\n\n| Resolution | Pixels | Raw storage |\n|---|---:|---:|\n| 1,024 × 1,024 | 1,048,576 | 4 MiB |\n| 2,048 × 2,048 | 4,194,304 | 16 MiB |\n| 4,096 × 4,096 | 16,777,216 | 64 MiB |\n| 8,192 × 8,192 | 67,108,864 | 256 MiB |\n| 16,384 × 16,384 | 268,435,456 | 1 GiB |\n\nThis gives us an engineering vocabulary without prematurely declaring the final galaxy resolution.\n\n## 7. Solar-system scale\n\nA system should have its own simulation density. At strategic distance it can be represented by aggregate state and a small number of strategic FSMs. When focused, it expands into orbital zones, installations, fleets, vehicles, facilities, squads, and individuals.\n\nA first candidate activity budget is:\n\n| System activity | Approximate active FSM scale |\n|---|---:|\n| Quiet / remote | 10²–10³ |\n| Economically active | 10³–10⁴ |\n| Militarily active | 10⁴–10⁵ |\n| Major battle / player focus | 10⁵–10⁶+ |\n\nThese are architecture exploration numbers, not performance guarantees.\n\n## 8. Galactic simulation\n\nThe hierarchy becomes:\n\nGalaxy → Sector → Star System → Region / Orbital Zone → Facility / Fleet → Vehicle / Structure → Squad → Soldier → FSM Instance\n\nThe global layer still ticks everywhere. Remote regions can use coarse strategic procedures while active regions execute more detailed procedures.\n\nA remote battle can still begin, escalate, end, consume ammunition, destroy equipment, produce casualties, change ownership, alter logistics, create veterans, and change political relationships.\n\n> **Distance reduces detail. It does not stop history.**\n\n## 9. FSM count is not entity count\n\nThese must remain separate.\n\nOne soldier may require dozens of FSM instances. One logistics procedure may coordinate hundreds of soldiers. One fleet procedure may coordinate hundreds of ships. One strategic faction procedure may influence thousands of organizations.\n\n> **Entity count is not simulation complexity. FSM work is simulation complexity.**\n\n## 10. Three kinds of memory\n\n### State memory\nSmall, frequently changing values: FSM state indexes, activity state, readiness, current phase, and simulation priority. This is the strongest candidate for packed GPU-friendly storage.\n\n### Semantic memory\nMeaningful world data: identity, relationships, ownership, inventory, equipment, qualifications, history, faction membership, and provenance.\n\n### Historical memory\nLong-lived records: battles, injuries, promotions, transfers, discoveries, production history, political decisions, treaties, betrayals, and deaths.\n\nHot state should not be forced to carry the entire history of the world.\n\n## 11. Event Horizons become the scaling mechanism\n\nThe simulation needs a reversible expansion/contraction operation:\n\nDetailed simulation → summarize → strategic state → later expand → detailed simulation\n\nWhen a player arrives, detail expands. When the event resolves or attention moves away, the simulation can contract again.\n\nCompression must preserve consequences: casualties, survivors, damaged equipment, ammunition expenditure, changed positions, injuries, promotions, captured equipment, ownership, morale, and political consequences.\n\n> **We may compress the work. We must not compress away the consequences.**\n\n## 12. First capacity target\n\nThe first implementation target should not be “simulate a galaxy of exactly X stars.”\n\nInstead we should demonstrate:\n1. a soldier with a meaningful multi-FSM state budget;\n2. thousands of soldiers sharing FSM definitions;\n3. a regional state field;\n4. systems changing at different simulation frequencies;\n5. expansion from strategic state into detailed state;\n6. contraction back into strategic state;\n7. measurement of bytes, transitions, events, and execution time at every level.\n\nOnly then should production-scale galaxy dimensions be selected.\n\n## 13. What remains deliberately open\n\n- exact FSM count per soldier;\n- exact state count per FSM;\n- exact bytes per semantic soldier record;\n- exact galaxy texture resolution;\n- 2D versus 3D versus tiled/sparse galactic fields;\n- number of stars and subdivisions;\n- GPU versus CPU ownership for each state class;\n- event queue representation;\n- persistence format;\n- maximum simultaneous high-fidelity entities;\n- multiplayer synchronization strategy.\n\nThese are engineering questions informed by desired scale, not arbitrary design constraints.\n\n## 14. Central principle\n\n> **Bytes describe the state. FSMs describe the behavior. Events describe the change. Event Horizons describe how much work is necessary now.**\n\nThat gives raWWar a path toward a galaxy-scale simulation in which the machine does not waste equal effort on every object merely because every object exists.
